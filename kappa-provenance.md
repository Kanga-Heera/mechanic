> **Note on this copy**: this audit was produced inside a larger research
> workspace than this repository. `mechanic/data/phase0_llm_labels.csv` is
> included here; the raw investigation scripts it cites
> (`scratchpad/kappa.py`, `scratchpad/part2_revalidation.py`,
> `scratchpad/audit_combine_mode_check.py`, `scratchpad/phase0_hand_labels.csv`,
> `scratchpad/sample_{sigma,elastic,splunk}.pkl`) are lab-notebook artifacts
> from that workspace and are not shipped in this repository. The findings
> and quoted figures below remain accurate; only the ability to re-run those
> exact scripts from a fresh clone of this repo alone does not carry over.

## 1. Question

This audit exists to answer one question, asked in preparation for a paper
citing this project: **where did the human ground-truth labels used to
calculate the reported Cohen's κ = 0.747 actually come from?**

The brief for this audit was explicit that no reported statistic should be
assumed valid, no missing data should be invented, and the classifier or
methodology must not be changed to make a number look better. This document
follows that brief: every claim below is either traced to a specific file
(marked **repository proves**) or flagged as inference/absence (marked
**not established**). Nothing was modified in the classifier or the
label data while producing this report; the one code change made
(`churn.py`'s diffing path, see the note at the end) is unrelated to κ and
is documented separately, not folded into this finding.

## 2. Reported result

**κ = 0.747** appears first in `mechanic/RESULTS.md` (and identically in an
older draft, `mechanic/results_and_changes.md`) labelled **"v2, after Tasks
1/3/4/5"** — 83.3% agreement, 16.7% (15/90) disagreement, n=90, "substantial"
per the project's own pre-registered interpretation bands at the time it
was reported.

The same document also already discloses, in a block-quote at the top of
its "Stage 2" section (`RESULTS.md:277-289`) and again in a later section
titled "The AND/OR fix, implemented, and everything re-run", that **0.747
is superseded** — it is described there as "a real, historically-accurate
checkpoint at the time it was measured... not the current state of the
classifier." This audit independently verifies that disclosure rather than
taking it on trust (Section 6).

## 3. Source of human labels

**File**: `mechanic/data/phase0_llm_labels.csv` (90 data rows: `repo,
index, rule_path, rule_name, llm_tier, automated_tier, agree, direction`).

**Repository proves**: this file is byte-identical, except for one column
header, to `scratchpad/phase0_hand_labels.csv` (`diff` shows exactly one
changed line: the header `hand_tier` → `llm_tier`; all 90 data rows are
unchanged). File mtimes: `phase0_hand_labels.csv` was last written
2026-08-21 21:40; `phase0_llm_labels.csv` 2026-08-22 15:28, about 18 hours
later. There is no git history to pin this more precisely (see Section 10)
— mtimes are the best available evidence and are consistent with, but do
not prove beyond doubt, a same-day rename.

**Repository proves, directly and explicitly**: the docstring of
`scratchpad/part2_revalidation.py` (the script that actually computed the
v2 kappa figures, including the one this csv's column-rename produced)
states, verbatim:

> "Does not re-sample or re-label - the CSV's `llm_tier` column is a frozen
> DEVELOPMENT-SET reference, **not human ground truth**. These labels were
> generated by an earlier session of this same assistant, reading each rule
> and assigning a tier - the same agent that designed the tier taxonomy and
> built the classifier being evaluated against them."

This is the project's own code disclosing that the labels are **LLM-
generated, not human-generated**, and generated by the same actor (an AI
assistant) that also designed the classification taxonomy and built the
classifier under evaluation.

**Sample size**: 90 rules (30 SigmaHQ, 30 Elastic, 30 Splunk). Confirmed
directly from the CSV row count and cross-checked against
`scratchpad/sample_{sigma,elastic,splunk}.pkl` (30 entries each, file
paths and rule names matching the CSV's `rule_path`/`rule_name` columns for
the entries spot-checked).

**Labelling categories**: `IOC`, `Artifact`, `Tool`, `TTP` (matches the
brief's expected vocabulary exactly - no silent renaming found).

**Labelling method, as described in `docs/phase0-findings.md`**: "Task 3 —
Hand-verification (30 rules/repo, `seed=42`)... Automated vs. hand-read,
reading the query/search/detection block directly... applied by a human
who can see relationships between fields" (`docs/phase0-findings.md:527-529`).
This document is written throughout in first-person singular ("I
classified it TTP on intent," "I didn't add them," "I hand-read a sample
before trusting the numbers," `docs/phase0-findings.md:427,545,513`) - a
narrative voice consistent with, and this audit concludes IS, the same AI
assistant's own voice across sessions, not a human researcher's separate
authorial voice, given the direct statement in `part2_revalidation.py`
quoted above. The word "hand" in "hand-verification" is being used in
these documents to mean "read directly by the labeller, not via the
tokenizer/classifier code path" - not "produced by a person's hand."

**Annotator information**: **not established**. No name, role, credential,
or any other identifying information for a human annotator appears
anywhere in the repository (`docs/`, `mechanic/*.md`, or any
`scratchpad/*.py` docstring) - searched directly, zero matches for
"annotator," "labeled by," "labelled by," "research assistant," "graduate
student," or "domain expert." Combined with `part2_revalidation.py`'s
explicit statement, the repository's own evidence is that there was no
human annotator for this set at all.

**One human, or multiple**: **not applicable** - given the above, this is
not a multi-rater or single-rater human study; it is a single LLM session's
output, later re-labelled in column name only.

**Independent of Mechanic, and before/after seeing predictions**: **not
independent**, on the repository's own evidence. Every row of
`phase0_llm_labels.csv` carries the label (`llm_tier`), an `automated_tier`
column, an `agree` boolean, AND a `direction` column (e.g.
`auto_under_scores`) computed by comparing the two - i.e. the artifact that
exists is a single table where the "hand"/LLM label and the automated
prediction and their comparison were assembled together, not two separately
saved, independently-timestamped files that were only joined afterward.
There is no evidence in the repository of a blinding step (e.g. a labelling
pass saved BEFORE any classifier was run, or a note that the labeller could
not see `automated_tier` while assigning `llm_tier`). This does not by
itself prove the label was influenced by seeing the prediction row-by-row -
but the repository provides no evidence it was blind, either, and the
single-artifact structure is the shape you would expect from a
non-blinded process. See Section 7 for the closely related development-set
question, which the repository DOES prove directly.

**Rules excluded**: 0. Confirmed by re-running `part2_revalidation.py`
today: "unscoreable/parse-failed among the 90: 0" for the `v2_full`
configuration (the config that reached 0.747-lineage figures).

## 6. Independent recalculation

**Sanity check (v1 baseline, n=90)** - `automated_tier` column (the frozen
v1 snapshot stored in the CSV itself) vs. `llm_tier`:

| | agreement | κ (project's hand-rolled formula) | κ (sklearn.metrics.cohen_kappa_score) |
|---|---:|---:|---:|
| v1 baseline | 57.8% | 0.4119 | 0.4119 |

Confirmed to 9 decimal places identical between the project's own
hand-rolled `cohen_kappa()` (in both `scratchpad/kappa.py` and
`scratchpad/part2_revalidation.py`) and `sklearn`'s reference
implementation, run independently for this audit. **The kappa calculation
method itself is correct** - any discrepancy in the headline number is not
a formula bug.

**Re-running the CURRENT classifier against the SAME 90-row set, today**
(`scratchpad/part2_revalidation.py`, executed live for this audit, `v2_full`
configuration - `use_structural=True, lists_mode="v2"`, which uses
`fragility.classify_rule`'s DEFAULT `combine_mode="and_or_aware"` since the
script does not override it):

    === v2_full (n=90) ===
    agreement=73.3% disagreement=24/90 (26.7%) kappa=0.615
    hand\auto        IOC  Artifact      Tool       TTP
    IOC                1         0         0         0
    Artifact           0        17         1         0
    Tool               0        12        21         0
    TTP                0        10         1        27

**Reported κ: 0.747. Recomputed κ (current code, same data): 0.615.**
These do not match, and the reason is fully identified, not mysterious:

Confirmed directly (isolated verification script,
`scratchpad/audit_combine_mode_check.py`, written for this audit and
inspectable), toggling ONLY `fragility.classify_rule`'s documented
`combine_mode` parameter against the CURRENT codebase, same 90 rows:

| combine_mode | n | agreement | κ |
|---|---:|---:|---:|
| `flat_max` (pre-AND/OR-fix behavior) | 90 | 86.7% | **0.800** |
| `and_or_aware` (current default) | 90 | 73.3% | **0.615** |

**κ=0.800 is exactly, precisely reproducible from the current repository**
by setting `combine_mode="flat_max"` - this number matches RESULTS.md's
own documented "v2, true final (after Task 8)" checkpoint (0.800, 86.7%
agreement) exactly. **κ=0.747 is NOT reproducible this way** - RESULTS.md's
own account places 0.747 chronologically BEFORE "Task 8" (a field-context
gate added to the tool-vocabulary lookup, `fragility.
field_carries_process_context`), and that change, unlike the AND/OR fix,
has no parameter or flag to disable in the current code - it is
unconditionally baked into `is_tool_value`/`field_carries_process_context`.
There is no mechanism currently in the repository to reconstruct the exact
pre-Task-8 classifier state, so 0.747 cannot be independently regenerated
from what exists today, even though the general SHAPE of the explanation
(an earlier development checkpoint, superseded first by Task 8's fix, then
by the AND/OR fix) is well supported by RESULTS.md's own narrative and by
the 0.800 figure's exact reproduction above.

**Confidence intervals**: RESULTS.md quotes a 95% bootstrap CI for
SigmaHQ-only kappa (e.g. "[0.524, 0.941]" at one checkpoint). Confirmed via
`part2_revalidation.py`'s `bootstrap_kappa_ci()`: a percentile bootstrap,
5,000 resamples, fixed `random.Random(seed=42)`, resampling PAIRS (hand,
auto) with replacement at the given n and recomputing kappa each time,
taking the [2.5%, 97.5%] percentiles of the resulting distribution. This is
a standard, correctly-implemented percentile bootstrap - no issue found
with the CI methodology itself.

## 7. Independence / leakage assessment

**Repository proves** (not inferred) the following circularity:

1. `phase0_llm_labels.csv`'s single-artifact structure (label + automated
   tier + agreement + disagreement-direction, all in one row, one file) is
   not evidence of a blind labelling pass - see Section 3.
2. The same 90-rule set's disagreements are the explicit, named basis for
   FIVE classifier fixes shipped in "v2" (`docs/phase0-findings.md:542-548`
   lists five causes of disagreement between the automated and hand/LLM
   labels; `fragility.py`'s own module docstring lists the same five
   causes, in the same order, as what v2 was built to fix: cross-platform
   tool catalogue, principled protected-literal list, EventID/syscall
   structural gating, negation-awareness, structural detectors). This is a
   direct, traceable, one-to-one mapping from "what this label set
   disagreed with the classifier about" to "what the classifier's code was
   then changed to do differently."
3. After each round of fixes, kappa was recomputed against the SAME 90-row
   set and reported as the headline validation figure (0.412 -> 0.747 ->
   0.800, all against the identical 90 rows, per RESULTS.md's own
   chronology).

This is the textbook shape of **development/evaluation reuse**: the same
labelled sample was used to both diagnose what the classifier should do
differently AND to report the classifier's final agreement figure. It is
not the "human independently labels, classifier independently predicts,
then compared" pattern the audit brief describes as the non-circular case.

**What this audit does NOT find evidence of**: label values being edited
AFTER seeing a specific disagreement in order to force agreement (i.e.
changing `llm_tier` itself to match `automated_tier` post hoc). The `agree`/
`direction` columns in the CSV record disagreements as disagreements, and
`docs/phase0-findings.md` reports a 42.2% v1 disagreement rate candidly,
including naming the classifier's own canonical worst-case example
(`proc_creation_win_renamed_binary_highly_relevant.yml`) as a hand=TTP/
automated=Tool disagreement it took real structural-detector work to fix.
There is no sign the LABELS were adjusted to chase the score - the
CLASSIFIER was, which is a different (still important, still worth
disclosing) kind of circularity than fabricating agreement.

## 8. Development vs. evaluation

**B does not hold. A holds, directly proven.** The same 90-rule,
LLM-generated label set was repeatedly used to both develop/tune the
classifier and to report the resulting kappa as a validation figure - see
Section 7's three points. This was never a frozen classifier evaluated
against labels withheld from development.

The one dataset in this repository that WAS held genuinely external to
classifier development is different, and worth naming precisely so it is
not conflated with the 90-row set: MITRE Center for Threat-Informed
Defense's own **Summiting the Pyramid (STP) ScoredAnalytics** dataset -
analytics scored by MITRE's own researchers, independently of this
project, against a published methodology (`RESULTS.md`, "Part 2, external
validation" section). That comparison reports **Kendall's tau-b = 0.361
(p=0.001)** against n=72 STP-scored analytics (a rank correlation on a
different construct/scale - STP's 1-5 analytic-robustness score - not a
4-category kappa against the same IOC/Artifact/Tool/TTP taxonomy), and is
the one genuinely external, non-circular check reported anywhere in this
project. It is NOT the source of κ=0.747; it is a separate, later,
methodologically distinct validation against a different dataset.

## 9. Result

**PARTIALLY CONFIRMED**, with the following precise breakdown:

- The number 0.747 itself, the calculation method, and the classifier
  version it was measured against are all real and consistent with the
  repository's documented history - this is not a fabricated figure.
- κ=0.747 is **NOT independently reproducible today** from the current
  repository state, because the classifier changed twice since it was
  measured (Task 8's field-context fix, then the AND/OR combination fix)
  and only one of those two changes has a toggle to reverse.
- The **label set it was measured against is not human ground truth** -
  the repository's own code explicitly documents this ("not human ground
  truth," `part2_revalidation.py`). It is a single AI assistant's own
  reading of each rule, produced by the same assistant that built the
  classifier and designed the taxonomy being scored.
- The label set was **used for classifier development, not held out** -
  proven directly by the one-to-one mapping between this set's documented
  disagreement causes and the classifier fixes that followed.
- The one figure in this project that IS both independently reproducible
  and evaluated against genuinely external, human-produced ground truth is
  **Kendall's tau-b = 0.361** against MITRE's STP ScoredAnalytics - a
  different number, different construct, different dataset from κ=0.747.

## 10. Problems found

1. **No git repository exists for this project.** `D:\sigma-research` and
   `D:\sigma-research\mechanic` have no `.git` directory - confirmed via
   `git rev-parse --is-inside-work-tree` failing at both locations. Only
   the third-party rule corpora being analyzed (SigmaHQ, Elastic, Splunk,
   etc., under `thirdparty/` and `sigma/`) are real git clones. This means
   Phase 11's requested commit-based timeline cannot be built at all - file
   modification timestamps are the only available substitute, and they are
   weak evidence (mutable, not cryptographically tied to content).
2. **The label set is not human ground truth**, contrary to what its
   original filename (`phase0_hand_labels.csv`) and its describing
   document's first-person "hand-verification" framing would suggest to a
   reader who has not also read `part2_revalidation.py`'s docstring. The
   rename to `llm_tier` is a real, positive correction that happened at
   some point in this project's history, but `docs/phase0-findings.md`
   (the document a reader is most likely to cite for methodology) still
   describes the process in "hand"/"human" language throughout and does
   not itself carry the same disclosure the CSV rename and
   `part2_revalidation.py`'s docstring do.
3. **κ=0.747 cannot be reproduced from the current codebase**, because one
   of the two classifier changes made since it was measured (Task 8's
   field-context gate) has no ablation toggle, unlike the AND/OR
   combination fix which does (`combine_mode`). 0.800 (the NEXT checkpoint
   after 0.747) is exactly reproducible; 0.747 itself is not.
4. **No annotator, human or otherwise, is named anywhere** for the 90-row
   set - not a name, not a role, not a credential.
5. **No sampling script was found** for the original 30-rules-per-repo,
   `seed=42` sample referenced in `docs/phase0-findings.md` - only the
   resulting pickled samples (`scratchpad/sample_{sigma,elastic,
   splunk}.pkl`) and a downstream dump utility
   (`scratchpad/dump_samples.py`) that reads them exist. The sample itself
   is a fixed, inspectable artifact; the process that produced it is not
   independently re-runnable from what's in the repository.
6. **The label artifact is not structured to demonstrate blindness** - see
   Section 3/7. This does not prove the label was influenced by the
   automated prediction, but the repository provides no evidence it
   wasn't, either.

## 11. Recommendation for the paper

**Do not cite κ = 0.747 as a validation result**, for two independent
reasons that each individually would be disqualifying, and which compound:
(a) the label set it was measured against is not human ground truth and
was used to develop the very classifier being scored against it, and (b)
the figure is not reproducible from the current codebase regardless of
label quality.

**What CAN be safely and precisely claimed**, each with an exact citation
back to this audit:

- "An internal, self-consistency check against a 90-rule, LLM-generated
  development set (not independent human ground truth; the same set used
  during classifier development) showed the classifier's agreement with
  its own earlier design intent improving from κ=0.412 to κ=0.800 across
  successive fixes, before a further, methodologically-motivated fix
  (correcting the AND/OR observable-combination rule to match STP's own
  documented methodology) reduced it to κ=0.615 aggregate / κ=0.298 on the
  Sigma-only subset - this reduction on a self-consistency metric is
  reported alongside the fix because the fix itself is independently
  justified by external validation (below), not because the drop is
  desirable."
- "The classifier's fragility tier was validated against MITRE Center for
  Threat-Informed Defense's Summiting the Pyramid (STP) ScoredAnalytics
  dataset - genuinely external, human-expert-scored, and never used during
  classifier development - and found to correlate positively and
  significantly with MITRE's own analytic-robustness scores (Kendall's
  tau-b = 0.361, p=0.001, n=72)." This is the number that can carry actual
  evidentiary weight in the paper.

**What a proper evaluation dataset would need**, if a real human-agreement
figure is wanted for the paper:

- Labels produced by a person (or, ideally, multiple people with a
  reported inter-rater reliability figure of their own) who did not design
  the classifier's taxonomy and was not otherwise involved in building it.
- The labeller working from the rule content alone, with no visibility
  into the classifier's own prediction for that rule, recorded via
  separate, timestamped artifacts (a labels file saved and hashed BEFORE
  any classifier run touches the same rules) rather than one combined
  table.
- A sample drawn by a script committed to the repository (or otherwise
  fully specified: corpus, glob pattern, seed, sampling function) so the
  exact rule set is independently regenerable, not only inspectable after
  the fact via a pickle.
- The classifier version pinned by an actual commit hash in a real git
  repository, so "which version was evaluated" is never again a question
  that has to be answered by cross-referencing prose checkpoints in a
  Markdown document.
- If the classifier is iterated on using ANY labelled sample, that sample
  must be clearly retired from ever being used again for a headline
  evaluation figure - a fresh, disjoint, held-out sample is needed for the
  number that goes in the paper.

## Secondary task: does the project have human ground truth for fragility classification?

**No independent human-labelled dataset for the 4-tier (IOC/Artifact/Tool/
TTP) fragility taxonomy was found anywhere in this repository.** The only
label set for this specific taxonomy (`phase0_llm_labels.csv`/
`phase0_hand_labels.csv`, 90 rows) is, per the project's own code
disclosure, LLM-generated by the classifier's own designer, not human. The
current κ result (whichever checkpoint - 0.412, 0.747, 0.800, or 0.615)
**cannot be independently validated as human agreement**, because the
underlying human-labelled dataset does not exist. The one dataset in this
project that IS genuinely external and human-produced (MITRE's STP
ScoredAnalytics) does not use this project's 4-tier taxonomy or Cohen's
kappa - it uses STP's own 1-5 scale and a rank-correlation statistic
instead, and is a real, if narrower and differently-shaped, source of
external validation. No replacement 4-tier human labels were created for
this audit, and none should be invented - see the recommendation above for
what a real one would need.
